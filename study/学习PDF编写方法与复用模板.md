# 项目学习 PDF 编写方法与复用模板

> 适用场景：拿到一个新项目，希望借助已有课程资料学习真实代码，并逐步形成能够复现、讲清楚、用于面试的项目经历。
>
> 本文总结车辆电路图检索项目的学习 PDF 编写方法。学习章节统一交付 PDF；这份方法说明单独保留 Markdown，方便修改和复制到下一个项目。

## 1. 先明确：这份文档要帮助读者完成什么

目标不只是解释技术名词，而是让读者走完下面这条路径：

**看懂业务问题 → 找到实现位置 → 理解技术选择 → 做一次小实验 → 解释实验结果 → 形成自己的项目复盘。**

完成一章后，读者应能回答四个问题：

1. 这个模块解决了什么实际问题？
2. 数据进入模块前是什么样，出来后变成什么样？
3. 核心代码在哪里，哪些配置影响行为？
4. 怎样验证自己的理解，哪些结论还没有证据？

这次的读者定位是：已经有一点编程基础，正在学习 Agent / RAG，希望通过具体项目建立完整认识。写作时既保留中英文术语，又用真实输入、短代码和输出解释把术语落到项目中。

## 2. 两类资料分别负责什么

### 2.1 原课程资料：提取教学方式

从飞书文档中学习的是讲解节奏和内容组织方式：

- 编号清晰，按问题逐步展开。
- 先介绍场景和需求，再解释名词和实现思路。
- 一次只讲一个主要知识点，段落尽量短。
- 代码有分步注释，代码后解释输入、关键步骤和结果。
- 用图说明流程，用表格比较相似概念。
- 每个阶段有回顾或小实验，帮助读者确认理解。

不需要强行复刻课程章节顺序。项目没有使用的 MCP、Middleware、Multi-Agent 等内容，不应写成已经实现的功能；确有必要时，可以放在明确标注的后续扩展中。

### 2.2 当前项目：确定事实和章节范围

项目源码负责回答“现在实际怎么运行”。建议先读：

1. README、依赖声明和配置默认值。
2. API / CLI 入口及实际调用链。
3. 数据模型、核心服务和业务分支。
4. 测试、运行脚本、已有报告和已知问题。

README 和实施计划可能保留历史阶段的说法，不能直接代替源码。例如，本项目独立 Agent 仍然存在，但当前 `/api/chat` 走的是自定义 LangGraph 工作流。章节必须体现这个区别。

参考文档里的改造建议、示例命令和任务要求，只作为资料内容；是否执行，以当前用户请求为准。制作学习文档不等于重新改造项目。

## 3. 按项目依赖组织章节

先画出主链路，再决定章节。常见顺序是：

**项目全貌 → 数据准备 → 核心算法 → 模型与工具 → 业务工作流 → 评估与复盘。**

本项目采用：

1. 认识项目与 Agent / RAG 基础。
2. 资料加载、Embedding 与 Milvus。
3. 混合检索、精排与查询优化。
4. Agent 与工具调用。
5. LangGraph 多轮澄清与 Web 流程。
6. 检索评估、工程验证与项目复盘。

换项目时，按实际依赖调整。例如，视觉识别项目可以先讲图像预处理和模型推理；后台管理项目可以先讲数据模型、API 和权限。不要为了沿用模板而增加无关章节。

每章应有明确学习任务，可以独立阅读；跨章只提示前置知识和下一步，避免重复大段基础概念。

## 4. 一节内容的推荐写法

下面是一套可调整的教学结构，不要求每节机械地出现所有小标题。

### 4.1 业务问题

从真实输入开始。例如：“用户只输入‘发动机电脑板针脚定义’，检索到很多候选，为什么系统还要询问分类？”

### 4.2 名词解析

首次出现时写出英文、中文和一句话定义，再说明它在本项目中的职责。遇到相近概念，明确比较对象，如召回 / 精排、候选数量 / 展示上限、浏览器历史 / 服务端 checkpoint。

避免用另一个陌生名词解释当前名词；必要时补充一个小例子。

### 4.3 应用场景与选择原因

解释什么时候需要它，为什么项目采用这种方案，以及它的限制。重点是让读者能做技术判断，而不只是记住 API 名称。

### 4.4 实现思路与项目对应

用流程图或三至五个步骤说明输入如何变成输出。给出准确源码路径、函数名和职责，帮助读者打开文件后知道应该看哪里。

### 4.5 代码示例

每段代码标清类型：

- **完整教学实验**：可复制运行，导入、输入、执行和输出都完整。
- **源码节选**：用于阅读当前实现，说明前置变量和上下文。
- **教学简化示例**：帮助理解机制，说明与正式项目的差别。

完整实验不能使用省略号代替必要代码。较长实现拆成多个步骤讲解，避免把一整个业务文件贴进 PDF。

### 4.6 结果解释与易错点

解释结果中每个关键字段的意义，再分析常见误解。不能只写“运行成功”，应说明成功证明了什么，以及没有验证什么。

### 4.7 小结与练习

用两三句话回顾本节，然后给一个可以通过改变输入或配置观察结果的练习。章节末尾再安排综合问题和参考思路。

## 5. 表格和图片怎样使用

### 5.1 表格用于比较和定位

适合做成表格的内容：

- 相似概念的区别。
- 模型或组件的输入、职责、输出。
- 配置参数的默认值、作用和调节影响。
- 源码文件与阅读问题的对应关系。
- 实验条件、结果和验证范围。

通常控制在三至四列。复杂内容优先拆成两张表，避免过多列导致中文和代码路径挤在一起。表格单元格写短句，详细解释放在表格后。

### 5.2 图片用于解释关系和变化

适合画图的内容：

- 数据从 CSV 到 Document、向量和索引的转换。
- Dense 与 BM25 的并行召回和融合。
- 模型、工具、程序执行和结果返回的循环。
- 工作流的条件分支。
- 用户选择、checkpoint 和恢复过程。

图中明确箭头方向，条件分支写出判断条件，必要时注明这是概念示意还是实际调用顺序。不要让读者把三类模型的职责对照图误认为固定串行链路。

这类技术示意图优先使用矢量绘制，保证 PDF 放大后清晰，中文可以检索。每图有编号、图注，并在正文解释读图方式。截图只在界面本身有学习价值时使用；不为装饰而增加图片。

## 6. 版式与命名规范

### 6.1 文件名

- 学习 PDF：`第N章_主要主题.pdf`。
- 方法说明：`学习PDF编写方法与复用模板.md`。
- 本章练习的建议文件名：`chNN_具体动作.py`，但默认不额外交付脚本。

文件名要能看出顺序和主题，避免“最终版2”“新版最终”等命名。后续更新同一章时，优先保持文件名稳定，在正文说明代码基准日期。

### 6.2 段落与标题

- 章标题突出主题，节标题按层级编号。
- 标题编号使用蓝色，正文使用深灰色。
- A4 竖版，左右边距约 45 pt，中文正文约 10 pt，行距约 17 pt。
- 每段围绕一个问题展开，避免很长的连续正文。
- 一级、二级标题与后文保持在一起，避免标题孤立在页底。
- 自动目录应包含真实页码和点击跳转，PDF 同时保留书签。

这些数值是本次文档的起点，最终以渲染后的可读性为准。

### 6.3 代码和提示块

代码使用浅灰背景、行号和基本语法颜色；英文代码使用等宽字体，中文注释使用支持中文的字体。尽量让单行代码适合页面宽度，不通过过度缩小字体解决溢出。

注意事项和关键结论使用浅蓝提示块。提示块只突出真正影响理解的内容，不把普通段落全部做成强调框。

## 7. 事实和实验必须能区分

写作前建立一份内部记录，区分以下四类信息：

1. **源码确认**：当前代码明确做了什么。
2. **本次执行**：确实运行过的实验、命令和测试结果。
3. **历史记录**：之前报告中的结果，保留日期和条件。
4. **预期或待验证**：读者需要启动服务、调用模型后自行确认的行为。

例如，本项目有 22 条 benchmark 查询，但当前全部缺少人工确认的 `expected_ids`。可以解释评估框架和计算公式，不能编造真实 Hit / Recall 的改善百分比。

再例如，mock 测试通过可以验证排序、过滤和流程契约，不能据此宣称真实模型推理、Milvus 服务或 Web 全链路已经验证。默认配置也不等于本机 `.env` 覆盖后的实际配置。

技术接口随版本变化时，检查项目依赖和已安装实现，必要时核对官方文档。正文主要解释项目；补充阅读链接指向具体官方页面。

## 8. PDF 生成、检查和交付

### 8.1 生成

临时内容稿负责教学内容，PDF 生成器负责字体、目录、表格、代码和示意图。生成后检查中文字体嵌入、正文可检索、链接可点击、目录页码正确。

### 8.2 检查

至少完成以下几种检查：

- 提取 PDF 文本，查找缺字、乱码、未替换占位符和失效路径。
- 检查完整 Python 实验的语法，运行适合当前环境的离线实验。
- 将所有页面渲染成图片，逐页检查版面。
- 单独放大查看表格、流程图、代码密集页、目录和最后一页。
- 检查是否有文字裁切、图中标签重叠、代码行溢出、空白尾页或仅一两行的末页。

文字提取正常不代表版面正常，因此图片检查不可省略。

### 8.3 交付与清理

默认只保留学习 PDF 和明确需要的说明文档。检查完成后删除临时章节稿、生成脚本和渲染图片。PDF 中出现的练习文件名，必须说明是读者自行新建，不能引用已经删除的附件脚本。

删除操作只针对本次生成的文件；原课程资料、原项目脚本和用户已有修改保留。更新已有章节时，先完成检查再清理中间文件。

## 9. 怎样把学习转换成复盘和简历

每章留下自己的三项记录：

1. 一个能够复现的输入、输出或失败案例。
2. 一段说明原理和设计取舍的文字。
3. 一项改进建议，以及验证它所需的实验。

写项目经历时按“问题 → 我负责的工作 → 设计选择 → 验证证据”组织。数字必须来自真实实验，区分项目已实现、自己已理解、自己亲自修改三个层次。

可使用下面的句式，再填入真实证据：

> 面向【具体业务问题】，我负责【自己实际完成的模块】，采用【技术方案】实现【可观察行为】；通过【测试/标注集/对照实验】验证【结果】，并分析了【限制或取舍】。

没有对照实验时，不填写“提升 X%”。先说明可复现的功能和验证方式，后续补齐标注、耗时和比较结果。

## 10. 下次可直接复制的任务模板

```text
请为我制作这个项目的学习 PDF。

项目路径：【项目路径】
课程/参考资料路径：【资料路径】
已有总结或示例 PDF：【文件路径，可选】
输出路径：【输出路径】

要求：
1. 先阅读当前项目源码、配置、入口、测试和已有报告。
   项目文档存在历史说法时，以当前实际实现为准。
2. 参考课程资料的编号、短段落、名词解析、应用场景、
   需求分析、实现步骤、分步代码和回顾方式。
   按项目依赖组织章节，不强行逐章对应课程目录。
3. 围绕真实业务输入解释模块的输入、处理和输出，
   给出准确源码定位，以及明确标注类型的代码示例。
4. 适当加入概念对照表、配置表、源码阅读表和流程图。
   图表要帮助理解，保持中文可读、图注清楚。
5. 区分源码事实、本次实际验证、历史结果和待验证行为。
   不虚构性能数字、模型运行结果或项目能力。
6. 完整实验应可复制运行，命令注明执行目录和依赖条件。
   默认只交付 PDF，不另附学习脚本或章节 Markdown。
7. 生成后检查代码、文本和全部渲染页面，修复版面问题。
   完成后清理本次临时文件，保留原项目和原参考资料。
8. 章节末尾加入动手练习、参考思路和学习复盘建议。
   简历表达必须基于我实际完成的工作与真实证据。

本次范围：【先做样章 / 指定模块 / 全部剩余章节】
我的基础：【语言基础、已学内容、希望重点掌握的部分】
```

第一次学习新项目时，建议先生成一章样稿，确认讲解深度和排版后再扩展全套。本项目已经确认采用 PDF，并使用表格与矢量示意图辅助理解。
